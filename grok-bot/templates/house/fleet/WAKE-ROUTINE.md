# Seat wake routine (template)

Why every wake runs station, with no exception: there is no pre-compaction hook, so a seat gets its rules back after a compaction only by re-reading the station skill and OP-PROC, and every wake is when that re-read happens. The rules are the named stanzas in [OP-PROC](../../../OP-PROC.md). This file is the webhook wake. It does not replace [Station boot](../../../OP-PROC.md#station-boot): step 1 is station Full and step 7 is the station way-out, on every wake with no exception. A chat turn, including a room turn, runs station itself; step 0 belongs to the webhook wake only. Forge owns the eng wave and the beat cut. Blinky does not cut an eng beat. When a beat or its last child closes, the forge wake runs `cutAfterClose` in `house/live/app/eng-wave.mjs` in that same turn. An empty inbox runs it too. The cut tips Arch1 and posts a ready handoff. It does not say the cut waits for forge chat. No next beat writes one `NOTES no-cut` line. An open Arch1 head blocks a second tip. `arch1_launch` off disables the Arch1 cloud worker only. It does not stop this inbox head. On wake, `live-inbox <seat> --ack stale --apply` clears closed-card tips. This seat does not wait for someone else to pop them.

A line `nudge:station:<seat>:<hour>` says to run station and re-read OP-PROC. Boot on every turn stays the rule. The poll is the reminder after a summary. A memory note is not that re-read. On that line, Full before `--ack`. Write one `Full: OP-PROC read` line on STATION after the read. `--prompt` is [Station boot](../../../OP-PROC.md#station-boot).

The prompt each seat installs as its webhook-triggered Bifrost inbox wake routine (inbox docs: `house/live/docs/inbox.md` in the repo). Copy the commands below as they are. Replace `<seat>` only. Set `XRAY_MAIN` to the main checkout. Set `SEAT_KEYS_DIR` and `LIVE_URL` as a folder or a URL name only, never a key value. These commands post straight to the board with the seat's own key. The box pusher is not in this routine.

This routine is the Bifrost inbox wake, and it sets `LIVE_URL`. A seat with no `LIVE_URL` does not use it: that seat reads and writes `house/WAVEBOARD.md`.

Env first, on every turn, in the same shell as the commands below. The routine runs `house/live/tools/live-inbox` from the main checkout (`XRAY_MAIN`). It does not run a copied binary, and it does not put `$HOME/.burst/bin` or `LIVE_INBOX_BIN` on `PATH`. The cursor folder rule is [Cursor folder](../../../OP-PROC.md#cursor-folder). A missing `LIVE_URL` or `SEAT_KEYS_DIR` exits 2 and names it. Another board may export its own `LIVE_URL` and `SEAT_KEYS_DIR` on the line before the block.

The wake never clones the repo and never makes a new checkout or worktree; the box bars both, and a wake that tries dies before station runs (xray#959). It updates the checkout that is already at `XRAY_MAIN` with the first lines of the block: fetch, fast-forward, then check that HEAD is origin/main. When the fetch or the fast-forward fails, or HEAD is not origin/main after it, the wake prints `wake: XRAY_MAIN not at origin/main (xray#959); stop`, exits 3, and reports `exit gate FAIL` with that line (step 7); it never runs live-inbox on a stale checkout. Read a file from main with `git -C "$XRAY_MAIN" show origin/main:<path>`.

```bash
# The file on main. Not ~/.burst/bin/live-inbox and not a copy under /tmp.
: "${XRAY_MAIN:?set XRAY_MAIN to the main checkout}"
git -C "$XRAY_MAIN" fetch -q origin main && git -C "$XRAY_MAIN" merge -q --ff-only origin/main \
  && [ "$(git -C "$XRAY_MAIN" rev-parse HEAD)" = "$(git -C "$XRAY_MAIN" rev-parse origin/main)" ] \
  || { echo "wake: XRAY_MAIN not at origin/main (xray#959); stop" >&2; exit 3; }
INBOX="$XRAY_MAIN/house/live/tools/live-inbox"
export LIVE_URL="${LIVE_URL:-https://bifrost.0xray.dev}"
export SEAT_KEYS_DIR="${SEAT_KEYS_DIR:-$HOME/.burst/seat-keys}"
export LIVE_CURSORS="$HOME/.burst/cursors"
export WAKE_RUN="${WAKE_RUN:-$$}"
# One token so the inbox monitor reprints the head once. --tag wake on the turn does not write it.
"$XRAY_MAIN/house/live/tools/inbox-wake-stamp.sh" <seat> || true
# LIVE_CURSOR_ROOT is empty here. A test sets it so the two absolute folders are under a temp dir.
root="${LIVE_CURSOR_ROOT:-}"
n=0
for d in "$HOME/.burst/cursors" "${root}/home/box/burst-run/cursors" "${root}/workspace/.cursors"; do
  if [ -f "$d/<seat>.txt" ]; then
    n=$((n + 1))
  fi
done
if [ "$n" -gt 1 ]; then
  "$INBOX" --migrate-cursors || exit $?
fi
trap '"$INBOX" <seat> --turn end --tag wake; "$INBOX" <seat> --release' EXIT
"$INBOX" <seat>
```

This is the line: On every owner message, first run `live-inbox <seat> --prompt --from owner --note "<gist>"`; after handling any inbox line (in chat or on a wake), ack it right away with `live-inbox <seat> --ack <id>` (or `--ack all` once everything open is handled); when you launch or resume a cloud agent run `live-inbox <seat> --turn start --tag "bc-<first8> <track>"` and `live-inbox <seat> --cloud launch --agent <bc-id> --tag <card>` (resume uses `--cloud reply`); when it finishes or is cancelled run `live-inbox <seat> --turn end --tag "bc-<first8>"` and `live-inbox <seat> --cloud finished --agent <bc-id> --tag <card>` (cancel uses `--cloud cancel`). The tag is owner/repo#n or xray#n. The cloud agent does not post that line. No exceptions for short turns.

Board rule. On every owner message run `live-inbox <seat> --prompt --from owner --note "<gist>"`. Ack a handled line with `live-inbox <seat> --ack <id>`, or `live-inbox <seat> --ack all` once every open line is handled. A cloud agent run uses `live-inbox <seat> --turn start --tag "bc-<first8> <track>"` beside `live-inbox <seat> --cloud launch --agent <bc-id> --tag <card>` on first start or `--cloud reply` on resume, and `live-inbox <seat> --turn end --tag "bc-<first8>"` beside `live-inbox <seat> --cloud finished --agent <bc-id> --tag <card>` (cancel is `--cloud cancel`). The tag is owner/repo#n or xray#n. The cloud agent does not post that line. `--from owner` is required today.

Kanban note. The live page shows a read-only kanban above Activity. Columns are open, review, fix, merge, retest, and done. The deep link is `?card=`.

History note. Every activity line is archived to history. The word owner is the owner via LIVE_OWNER or the owner-name.

0. List the open inbox first with the command above (`$XRAY_MAIN/house/live/tools/live-inbox <seat>`). That export sets `LIVE_URL` and `SEAT_KEYS_DIR`. A read does not write `<seat>.txt`. Only `live-inbox <seat> --remember` writes that file. The cursor folder rule is [Cursor folder](../../../OP-PROC.md#cursor-folder). On an owner message (a 1:1 or a room), before an empty inbox stops the turn, run `live-inbox <seat> --prompt --from owner --note "<gist>"` once, even when that read is empty or every line is a repeat, and add `--room <name>` when the message was in a room. A turn that missed its `--prompt` posts it later with `--at <ISO-8601 with offset>` set to the owner message's real send time, never the time of the backfill; `--at` does not post a second line for the same owner and seat within 2s. After handling any inbox line, ack it with `live-inbox <seat> --ack <id>` or `--ack all`. When you launch or resume a cloud agent run `live-inbox <seat> --turn start --tag "bc-<first8> <track>"` and `live-inbox <seat> --cloud launch --agent <bc-id> --tag <card>` (resume uses `--cloud reply`); when it finishes or is cancelled run `live-inbox <seat> --turn end --tag "bc-<first8>"` and `live-inbox <seat> --cloud finished --agent <bc-id> --tag <card>` (cancel uses `--cloud cancel`). The tag is owner/repo#n or xray#n. The cloud agent does not post that line. This webhook wake then runs `live-inbox <seat> --turn start --tag wake`. The tool posts no turn start and posts no turn end when another live wake of this seat already holds the claim, and only that claim's owner token may release it or post its turn end: that run prints nothing and does not ack the first run's lines. Before any ack, do step 1 and read the station ticket. Decide a repeat with a cheap handled-record read, `live-inbox <seat> --repeat --pr <owner/repo#n> --sha <head> --kind <kind>`, which checks the per-seat cursor key `repo#number|sha|kind`. The claim is not that record. The `--repeat` gate sets the order for every seat, the CoS seat included. When `--repeat` exits 1 (new, and a new head is always new), handle the line first, then record it with `live-inbox <seat> --remember --pr <owner/repo#n> --sha <head> --kind <kind>`, then ack it with `live-inbox <seat> --ack <id>`. For the CoS seat, handling a dev line means no implementation, no 1:1, and no handoff. After `--remember`, `--repeat` exits 0, and only then is the line acked, so "the CoS seat only acks a dev line" (step 3) comes after this order, never before it. A line that says the seat is still waiting, or that nothing changed, gets no GitHub comment: record it on the board only, with a NOTES line citing the existing issue or pull URL and `--remember` then `--ack <id>`, and it does not stop a newer line (xray#976). A still-waiting stop still runs step 7 and then exits through the shell trap. The trap posts turn end and then release on any exit, including a crash, so the claim does not hide the lines while the pid is still alive and the turn still closes. A duplicate or a still-waiting delivery is a quick check: the wake does not launch or resume a cloud agent for it, and steps 1 and 7 still run. A new line keeps the full boot read below. An early return still runs step 7.
1. Boot read, every turn (a compaction is a wake). Before that read, follow [Inbox watcher](../../../OP-PROC.md#inbox-watcher). A packet and its card follow [Packet](../../../OP-PROC.md#packet). The card key is the issue or pull. Do not hand-post a card. Grok Bot wakes never run `.cursor` hooks, so this step is the boot hook. Read `.xray/state/STATION.md` (the station ticket; never hand-edit it), then `.xray/state/NOTES.md` (the working page), then this seat's Bifrost cards (`GET /cards` on `LIVE_URL`), and resume the same role and job. If STATION.md is missing, or its `Fresh:` line names an older package than `node_modules/0xray/package.json`, run `npx 0xray wear` once and read it again; if it's still stale, append one line to NOTES.md and go on. If NOTES.md is missing, create it with `Point:`, `Open:`, `Learned:` and `Next cut:` lines (no secrets) before step 2. This wake is station Full: also read the file named by the HOUSE.md `OP-PROC:` line, the newest two NOTES entries, `ops/cloud-memory/TRACKS.md` in the suit, open board cards, and the STATION `Skills:` line. Light, on an owner message that is not a summary, a wake, or a gate, is the prompt plus STATION.md and does not read the pack.
2. Read your inbox: `live-inbox <seat>`. A non-empty read is the work. An empty read with nothing owed leaves steps 3 and 4 with no line to handle and posts nothing in a room. Steps 1, 5, 6 and 7 run as on every wake: one NOTES.md `##` entry with the time and the inbox state, the STATION `Working:` line, TRACKS, the exit gate, and the closing line from the trap.
3. If this seat is A and a same-path cluster is open, tip that bundle once and do not open the pull. The rule is [Bundle](../../../OP-PROC.md#bundle). An open solo tip stays solo. Handle each open line, then ack it: `live-inbox <seat> --ack <id>`. Post a GitHub comment only when the line needs a new answer carrying a real change: a new head sha, a review verdict, a CI result, a handoff, or a decision. No-comment rule (xray#976): a still-waiting or nothing-changed line is recorded on the board (a NOTES line plus `--remember` and `--ack`) and never gets a GitHub comment. A nudge (L1, L2, L3, or station) is answered on the board only, never on GitHub: the ack is the answer. A seat never posts a comment that only acknowledges another seat's comment ("Seen", "Received", "Still waiting"); a comment a fleet seat bot wrote does not wake another fleet seat unless it carries a real change, but a seat outside the fleet (the roster's `outside` list, Arch1) is never filtered: tip Arch1 by @-mentioning him in a GitHub comment and that comment still wakes him. More than 3 fleet-seat comments on one issue or pull in an hour pauses wakes for the fleet seats on it (never Arch1) and files one `needs_human` line for Blaze. A wake that must say it is waiting cites the existing issue or pull URL in NOTES; the exit gate accepts that and does not need a new comment. Closed or merged lines are `live-inbox <seat> --ack stale` and then `--apply`. `--upto <id>` acks the stored prefix through that id, including live lines. `--ack all` acks every open line. A missing card, and an old handoff on a live card, stay until `--ack <id>`. When this seat owes a handoff, and this seat is not the CoS seat, run `live-inbox <seat> --handoff <to> --pr <owner/repo#n> --kind <ready|critic_fail|live_pass|merge|ci_fail> --sha <head>` and send the printed line as a 1:1. The CoS seat does not post a handoff. The CoS seat only acks a dev line, in the step 0 `--repeat` order, and sends no message about it. The CoS seat acts only on next-wave planning, burn pacing, H-lane and Dist packets, and seat onboarding. A room post is never a handoff and never a wake: seats may not ack in a room, so a room receipt cannot be relied on.
4. A webhook wake never launches or resumes a cloud agent. On a duplicate or a still-waiting delivery it records the event and ends through step 7; otherwise it records the event and hands off to the owner's chat (forge for builds, critic for reviews) with a seat message pointing at the card. The server rings that seat message on the chat doorbell for a critic ready or green head. The ring is not a cloud resume. Only the owner's persistent chat launches or resumes a cloud agent. That chat reads `GET /cards` first. It does not launch or resume when the card id is missing. A missing id is not a launch. The cloud agent pushes its branch only. The seat App opens the pull request. The server attaches that branch and that pull request to the same card. The activity line gains no new field. Write the cloud id to `ops/cloud-memory/TRACKS.md` in the suit in the launch step. On the way out write the card metadata: title, url, owner seat, stage, and state. A cloud agent pushes its branch only and never opens a pull request or an issue. The wake sends only a flushed batch: one inbox line whose `batch` string is the collapsed critic review, CI, and handoff for that head. `run_end` (posted by that same chat) and `ci_pass` are the only flushes. A new head does not flush a run that is still live. A green head queues critic on `run_end` when the checks are already green, and on `ci_pass` when the run has already ended. A green event seen before `run_end` is not replayed. A head is red only after a required check has failed; a pending check waits, and a red head goes back to the worker with the batch. Before any launch, that chat reads `house/ATTENTION_STATE.md` and does not launch when the day is over pace or weekly burn is at 75% or more, except a hotfix. The card stores `critic_bc`, the critic cloud id for that PR. On a new head the critic chat resumes `critic_bc` and launches a new agent only when the card has no `critic_bc` or that resume is refused. One critic agent per PR. Deep search and thinking still run on a cloud agent: a diff, a fix, code search, tests, every review, and every live pass. Mechanical steps stay on the wake: a head-SHA check, a review-list check, a verdict the cloud already wrote, inbox acks, handoffs, and NOTES lines. One critic verdict per head. The agent wears the suit first (plates, the station ticket, the notes). Never hand-edit the station ticket to record this.
5. Notes after every beat: append to `.xray/state/NOTES.md` right after each real beat (PR opened or pushed, verdict, CI result, merge, deploy, handoff, blocker, cloud agent launch or cancel), with evidence (links, SHAs, comment ids). There is no pre-compact signal, so continuous writes are the only protection.
6. Last, update `.xray/state/NOTES.md`: the intent and the next cut. No secrets: never a key, token or PEM text, only the env var name where a secret lives. Never commit NOTES.md.
7. Before the shell exits, run `node "$XRAY_MAIN/house/live/tools/exit-gate.mjs" .xray/state/NOTES.md`. If this turn merged a pull, the same section must say `closed repo#n` for every issue that pull fixed. A named bug, gap, follow-up, or ask with no `repo#n` or GitHub issue, pull, or comment URL fails the turn. The gate reads the first `##` section of that file. Notes are prepended, so that section is this turn. A non-zero exit fails the turn: write or fix that NOTES entry and run the gate once more. A wake whose last gate run did not exit 0 never says done, filed, or wrote in any reply, room post, or board line; it prints `exit gate FAIL` with the gate's message, says the same in its reply, and leaves the next fix for the next turn. Then ask: anything new without a card? File each new item as a card in this turn: a one-line what, `From:`, `Waiting on:` (a condition, or `nothing`), and `Owner:`. The rule is Fallout in `grok-bot/OP-PROC.md`. That filing finishes before turn end. Turn end is the EXIT trap above. That one close posts `live-inbox <seat> --turn end --tag wake` and then releases the claim. It runs on every exit, including an early return (empty inbox, early return, error) and a crash. The seat does not post it again before the shell exits. Turn end clears the working mark. From the suit folder, run `R=node_modules/0xray/scripts/node/auto-reflection-generator.mjs; if [ -f "$R" ]; then node "$R" --trigger commit-threshold; else echo "reflection: not run, no node_modules/0xray (xray#955)"; fi`. A missing package prints that one line and the wake goes on; doctor already flags the missing `node_modules/0xray/package.json`. The file lands in `.xray/state/repertoire/feedback`. That command does not run synthesis or confer.

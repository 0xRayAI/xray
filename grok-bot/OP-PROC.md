# Operating procedure

How the roles work. Read this first. Who you are, where you post, and which repos you may push live in `house/`. If that folder is missing, start from `templates/house/`. Name your seats anything. [Example house (names are illustrative)](templates/house/EXAMPLE.md). Every term here is defined in the [lexicon](LEXICON.md); if they disagree, the lexicon wins.
This file is the single source of truth. One rule is stated once, in one named stanza here, or in `house/OP-PROC.md` when the rule is house-only. Every other file links to that stanza instead of restating it. A sentence a test requires verbatim stays only where the test reads it.

- **Two loops.** <a id="two-loops"></a> All work lives in GitHub: one issue or PR per task, on its own branch and worktree, never on main. Anyone outside the fleet, such as Arch1, another fleet or a maintainer, is reached only by issue, PR or comment, @-mentioning who acts next. That is the outer loop, and it is what becomes cards, nudges and tripwire. Inside the fleet, seats wake each other with direct messages, and each message points to that issue, PR or packet. A direct message with no GitHub record is not work. To reach someone outside the fleet, @-mention them in an issue, PR or comment. The collector turns that comment into their inbox line, which is what wakes them, so never post to their inbox separately. The mention must be their real GitHub login: before @-mentioning anyone, look up their login at the Bifrost server's `GET /routing`, never from memory (`bifrost init --check` fails a nickname-only route).
- **OP cycle.** <a id="op-cycle"></a> Blaze, 2026-10-28: digest it · card it · do it · loop it · ship it.
  - Digest. Dig from disk (the station card, this file, the board), not from chat lore.
  - Card. A Bifrost card in the same turn. Without one it is a distant memory ([Card](#card)).
  - Do. The implementer does the work ([Roles](#roles)).
  - Loop. Two loops: the outer GitHub record, and the inner wake, volley, and critic ([Two loops](#two-loops)).
  - Ship. The publisher merges after the Review tier ([Review](#review)).
- **Coordinator never:** <a id="coordinator-never"></a> deploy, publish a package, change production, launch a cloud agent, post in public, spend, or merge. A seat never merges code it wrote: the cloud agent forge launches writes the code and pushes the branch; forge opens the PR through its App, and keeps continuity, gates and the merge chain.
- **Roles:** <a id="roles"></a> The seat field is the role, not a personal name. Code, pull requests, cloud work, deploys, and package publish = **implementer**. Shipping after review = **publisher**. Ship, live, security, and identity review = **reviewer** (a short note, no merge). Public posts, listings, and audio are optional **specialists**. The coordinator is also called CoS. CoS plans the next wave at each close (carded on Bifrost), paces burn, friend-tests Lane H and writes Dist packets, and onboards seats (suit fitting included). CoS lists a finished or idle seat; Blaze deletes it. CoS does not assign dev work. Dev talk is Blaze and forge. The cos-forge 1:1 carries the printed `live-inbox` handoff line. A room post is not a handoff. Money, credentials, and deletes = the **human owner**. **New seat before any ship work:** run `seat-label` in that seat's own chat; clear role description; fasten suit (mill+inspect) with inspect receipt on disk (`ok: true`, suit fastened, costume false); orientation + KB (role card, scope, grow mem from receipts); seat reads KT/orientation and acks before first carded job; if role was announced publicly, standing ROLE board card matching the announcement; CoS cards first work — seat quiet until carded; a new seat starts with only its profile + new-hire packet. A chat packet alone is not a suit.
- **Card:** <a id="card"></a> Blaze, 2026-10-21: "If it does not have a card, it is a distant memory." Work, follow-ups, or fallout without a Bifrost card count as forgotten, so card them in the same turn. One GitHub issue or pull request (`repo#number`). Fields: title, url, owner seat, stage (`open` > `review` > `fix` > `merge` > `retest` > `done`), state (`live`, `held`, `parked`, or `closed`). A chat ping is not a card. A card may carry `start_after`, an ISO time with a Chicago offset (`America/Chicago`, `-05:00` or `-06:00`). Until that time the card stays parked: no nudge, no tripwire, no empty-board pull. At that time the server wakes the owning seat through the normal inbox wake. Set it with `live-inbox <seat> --card owner/repo#n --start-after <ISO>`, or with a GitHub comment whose first line is `Start after: <ISO>`. The command wins while it is stored. The date is on disk, so a restart still honors it. A packet post creates the board card. The card id is `repo#number` when the packet names a positive number. A non-positive number, including zero, uses `packet:<line id>` until a pull request attaches, and then the id becomes `repo#number`. One card per id. The owner's chat does not launch or resume a cloud agent when the card id is missing. On the way out the seat writes the card title, url, owner seat, stage, and state. Fallout: anything that falls out (a deferred item, a held plate, a review follow-up, an owner later, a bug a researcher finds) becomes a GitHub issue in that turn, opened by the seat that notices it. The card carries a one-line what, `From:`, `Waiting on:` (a condition, or `nothing`), and `Owner:`. `Waiting on:` is a field, and the board may show those cards as a view. Stages stay the six names above. An unknown stage throws when `house/live/feed/live_board.py` sorts with `STAGES.index`. The archive card row already stores `waiting` and `hold` (`house/live/app/archive.mjs`). `Waiting on: #N merged` or `Waiting on: #N closed` releases on that merge or close. Conjoin is not a release. The board then lists every card waiting on it. A release appends a new archive row. The id is `key|stage|state|updated` (`recordId` in `house/live/app/archive.mjs`). A repeated id is not stored. The release changes the state or the update time, and the earlier row stays. `cardHistory` keeps every stored row. At turn end `grok-bot/skills/station/SKILL.md` asks: anything new without a card? A wake asks the same question in step 7 of `templates/house/fleet/WAKE-ROUTINE.md` and files each new item before the EXIT trap. The station-card lens is `.agents/skills/station-card/SKILL.md`. A miss becomes a new card and never fails the pull request under review. A cloud report ends with the Fell out list in `grok-bot/ops/cloud-memory/PROMPT-FOOTER.md`. Forge cards each line before replying. Board code stays as it is. The follow-up pull request parses `Waiting on:` and its unit test shows the waiting card is still in `cardHistory` after the release. Auto-creating cards from chat stays out of scope.
- **Packet:** <a id="packet"></a> the card's fields — goal, constraints, path, acceptance, gates, evidence, next owner, escalate, raci. `gates:` is set by the implementer; the reviewer may raise it, never lower it; it locks once review starts. `raci` names who does the work (R) and who answers (A). They come from a `## Packet` block in the issue or pull request body, or from one line. Each field is at most 200 characters, and links are allowlisted. A live card missing R or A is amber on its own mark. That mark is not the PACKET.md badge. The `needs a brief` badge is a packet PR whose PACKET.md is missing. Evidence fills from the latest beat. Posting the packet (`POST /inbox`, including a handoff) creates the card when the board does not already have that id. A chat line that never hits the board is still not a card.
- **Handoff = packet + wake** <a id="handoff-packet-wake"></a> (the inner loop of **Two loops**). The seat that owes it runs `live-inbox <seat> --handoff <to> --pr <owner/repo#n> --kind <ready|critic_fail|live_pass|merge|ci_fail> --sha <head>`. That posts one inbox packet. The seat sends the printed line as a 1:1. A **room post** is never a handoff and never a wake. Seats may not ack in rooms (they might or might not), so a room receipt cannot be relied on. A room post that names the next seat does not discharge the handoff, including a CoS room post. The cos-forge 1:1 carries the printed line when the handoff is CoS↔forge. If the packet is missing for `NUDGE_L1_S`, the card is flagged `handoff missing` and the owing seat is nudged L1, then L2, then L3. The server does not post the packet. A webhook is a doorbell after the packet exists. It does not replace the 1:1. A non-empty read is the work. A tracked packet moves `sent` → `delivered` → `woken` → `acked`, and is `overdue` past `NUDGE_L1_S`. Kinds on a tracked packet are `dispatch`, `ready`, `packet`, `critic_fail`, `needs_human`, or a blocker (`needs_human`, or `to` = `WORK_HUMAN_TO` on the `WORK_HUMAN_LANE` lane). Handoff kinds are `ready`, `critic_fail`, `live_pass`, `merge`, and `ci_fail`. A line that only names `from` is not a packet.
- **Pulsar.** <a id="pulsar"></a> The pulsar 🔫 spots a new back and gives that seat the whole board for the wave the board has up. The board names that wave in `house/bifrost-waves.json`, and Bifrost when `LIVE_URL` is set. One wave is on the board at a time. The hold ends when the board closes that wave. For that wave it overrides who owns the open cards. Production, publish, spend, secrets, deletes, and a critic PASS the tier already requires stay in force. When the wave ends, confer says whether the holder used it well: a yes moves them up the pick, a no moves them down and leaves them on the table, and three nos in a row sit them out for the next wave. One solar ban hammer pass is the only override of that confer, and it covers one pick. The initial and the selected seat live in `house/OP-PROC.md`.
- **Activity key.** <a id="activity-key"></a> `POST /activity` uses that seat's `SEAT_KEYS` entry. The seat posts only as itself (its id, alias, or `SEAT_DISPLAY_NAMES` label). A cross-seat `seat` is `403` `seat mismatch`. Builder still uses its GitHub App token.
- **Working.** <a id="working"></a> Three writers, and they stack. An open turn (`applyStoredActivity`) expires after `LIVE_TURN_OPEN_MIN` (default 20) if the ack never comes. A turn `end` or an ack clears working. The turn end still clears after `TURN_OPEN_MS`. The drop clears a mark at or before the end. A mark newer than the end stays only while it is inside `TURN_OPEN_MS` (20 minutes, `LIVE_TURN_OPEN_MIN`), then it expires. Newer GitHub marks expire at 20 minutes. A cloud turn tagged `bc-<id>` or `bc-<id> <track>` marks that agent, not the seat that posted it and not another seat. A mark with no time stays. A woken packet (`applyTrackWorking`) sets the chip `working_on`. A running cloud agent does not. A GitHub comment, review, PR opened or pushed, or issue event (`applyGithubWorking`) marks the actor's seat working for that same window, with `working_on` = `repo#number`. The card clock ignores CI and `pr_commit` on both sides it compares. A card-worthy event on a closed card is not a stall. A `pr_open` the board has not carded still is. The actor login maps through `inbox-roles.json`, `fleet-nodes.json` / `LIVE_NODE_MAP`, `LIVE_GH_SEATS`, and `git:<seat>` (`SEAT_GIT_NAMES`). A cloud agent maps through `SEAT_AGENT_MAP` or a `bc-` id in the branch or comment. `critic0x[bot]` is critic. `forge0x1[bot]` is forge. `CURSOR_WEBHOOK_SECRET` (32 characters or more) signs `POST /cursor/webhook`; shorter or unset, the launch does not register one. The chain is `house/live/docs/work-tracking.md`. A close or a merge of the item in `working_on` clears that chip on the seat and in `fleet.working`. The seat can stay working. `POST /activity/ingest` is the box-uploader exception to the per-seat pin (`house/live/docs/activity-upload.md`).
- **Beat:** <a id="beat"></a> one real event — a pull request opened or pushed, a review APPROVED (Reviewer PASS) or CHANGES_REQUESTED (Reviewer FIX), a merge, a reopen, a merge-queue tick, an owner message, a fleet seat's comment, a blocker, or a finished deploy (deploy, deploy_fail). CI stays on the card and is not board traffic. A draft parks at once. A live pull request with no beat for 72 hours parks. A reopen clears closed and stop. A merge or a close sends an info line to the author's seat. burst-live is the board, never a node. A watcher run whose start and end fall in the same second is never a beat. An idle loop on parked work is theater. The station is the survival strip. Wake on a PR, a person, or a compact.
- **Routing.** <a id="routing"></a> Every seat has a route in `inbox-roles.json`, and every route @-mentions the seat's real GitHub login, not only its nickname. The routing map lists each seat once with that login and its nicknames as aliases; the server resolves every login on GitHub and refuses one that does not resolve. Bifrost does not work without it: `bifrost init` writes it, `bifrost init --check` fails on a missing or nickname-only route.

Light is that step on every owner message. Full is after a summary, a wake, or a gate: the file named on the HOUSE.md `OP-PROC:` line, the newest two NOTES entries, TRACKS, open board cards, and the STATION `Skills:` line. Light does not read the pack. On the way out, update STATION judgement, the card, TRACKS, and the closing activity line, and ask anything new without a card. A new seat runs [seat-label](skills/seat-label/SKILL.md) in its own chat (`UpdateProfile` with `title` only, then `profile.json`). GitHub calls use [seat-github-key](skills/seat-github-key/SKILL.md) (`~/bin/gh-<seat>`). Profile planes are core, integration, ecosystem, distribution, and live. The public board is https://bifrost.0xray.dev. The docs site is https://docs.0xray.dev/. `--prompt` is owner-only. Add `--room <name>` when that owner message was in a room. A seat DM and a room message from anyone else do not post `--prompt`. The gist is 1–240 characters and is not the message text. A DM, a room post, and any inbound message text stay out of `--note` and `--tag`. A failed post (missing env, 401, 429, no network) is one line, with no retry and no local file. Continue the reply, and still run turn end on the way out. When the prompt is why an issue or pull request is opened, put `Prompt: <id>` in the body. The id is the `id` in the `{ok, id}` line. The key is never printed. A webhook wake uses [WAKE-ROUTINE](templates/house/fleet/WAKE-ROUTINE.md) for its one prompt, turn start, and turn end, and does not also run station. A chat turn uses station and does not also run WAKE-ROUTINE step 0. The logged command is the next line.

- **Ack.** <a id="ack"></a> A seat acks an inbox line with `live-inbox <seat> --ack <id>` after it handles the line. `live-inbox <seat> --ack stale` lists lines with a close or merge event, or a closed or done card, and does not ack them until `--apply`. A missing card stays, and so does an old handoff whose card is still live. `--upto <id>` acks the stored prefix through that id, including live lines. `--ack all` acks every open line at once. An ack is a plain seat-key call and never raises an approval card. Every seat runs the export line in `templates/house/fleet/WAKE-ROUTINE.md` before any `live-inbox` command. It sets `LIVE_URL` and `SEAT_KEYS_DIR`. `live-inbox` exits 2 and names a missing one. The cursor folder is [Cursor folder](#cursor-folder). Run `house/live/tools/live-inbox` from the main checkout, never a copy under `~/.burst/bin` or in `/tmp`.

Only `live-inbox <seat> --remember --pr <owner/repo#n> --sha <head> --kind <kind>` appends the key `repo#number|sha|kind`. `LIVE_CURSORS` is not required. Unset, the folder is `$HOME/.burst/cursors`. A `LIVE_CURSORS` value that names `/home/box/burst-run/cursors` or `/workspace/.cursors` exits 2. `LIVE_CURSOR_ROOT` is empty in production. A test sets it so those two absolute folders land under a temp dir. If `<seat>.txt` is in more than one of `$HOME/.burst/cursors`, `/home/box/burst-run/cursors`, and `/workspace/.cursors`, `live-inbox --migrate-cursors` runs once. It unions handled keys, including keys that sit only in a `*.txt.migrated` backup, into `$HOME/.burst/cursors`, keeps the newest copy of each key, and writes that file before it renames anything. `.claims.json` and `.lock` are copied from the newest file only. They are not merged. Old files are renamed to `*.migrated`. An existing `*.migrated` is left as it is. A later split exits 2 and names the paths. The wake and the watch scripts run `$XRAY_MAIN/house/live/tools/live-inbox`. They do not run a copy under `~/.burst/bin`.
- **Tripwire.** <a id="tripwire"></a> When nothing has moved for the trip window, the tripwire starts the timed run once per window: an empty board wakes the coordinator to pull the next work, unless weekly burn is at or above 75% (`BIFROST_WEEKLY_BURN` of `0.75` or `75`), which keeps that empty-board wake quiet and wakes no seat. Below 75% the empty board still wakes the coordinator. A stalled board wakes each seat with open work. A due plan card does not replace that stall wake. When a real wave's last card is closed or merged, the board raises one **plan next wave** card for the coordinator, naming the next open wave. The window is a Chicago cron (`0 9 * * 1` by default, Monday 09:00 America/Chicago). The due time stays on the card, so a restart does not re-arm it. Weekly burn at 75% keeps that plan card quiet. A plan card older than 7 days closes as expired and is not raised again for that same wave. The tripwire flags the card `nothing carded` when the window passes with no new card.
- **Nudge.** <a id="nudge"></a> A live card with no beat: L1 goes to the next owner, or else the card owner. L3 repeats to that L1 seat. An unacked inbox line steps L1, L2, and L3 on that same seat. A line the seat already acked, or whose handled key is already in the [cursor folder](#cursor-folder), gets no L1, L2, or L3. A missing handoff nudges the owing seat at L1, then L2, then L3. The owner fixes its own card. Bifrost keeps the board. CoS is not woken to reassign. A `Start after:` comment counts only from the card owner or a fleet seat. A stranger's comment is ignored. A time more than 30 days after now is ignored. The card field `merged_by` is the merger, never the author.

- **Done** <a id="done"></a> = a live receipt (a URL, a registry view, a GitHub Release URL, or reviewer PASS). Green CI is only gate A. Gates: A CI green, B the pack installs, C the docs match, D published and proven live (fresh install and upgrade, annotated tag pushed, GitHub Release so Latest flips). A pushed tag alone is FAIL for gate D. **Floor:** gates A and C on every merge. Doc-only updates: see [Review](#review). B and D are set per PR by scope (subsystem, module, component touched) in the packet's `gates:` field: does it work across all TUI environments, and are the docs updated throughout. Per-scope criteria: set per PR for now. TUI environments: Cursor, Grok CLI, Hermes, OpenCode, OpenClaw. **Gate B runs on the owner's machine** (seat computers lack these environments): when `gates:` calls for B, the packed tarball plus a per-environment checklist (git and non-git folder, temp home, run and update the `.cjs`/`.mjs` files for each TUI environment) is run either by a seat through owner-approved local tool steps, or handed to the deep-review seat in a PR comment when it runs locally there. Cloud runs (cloud agents, cloud deep review) never satisfy B. Whoever runs it posts the receipt; B stays unverified until that receipt exists. A chat "looks good" is not done.
- **Review:** <a id="review"></a> Light and Normal = the reviewer's Light PASS + CI before merge (green CI alone never merges). A hotfix is the one exception: it merges only on green CI, never before. Blaze's 09:36 CT ruling, 2026-10-21: doc-only updates do not require tests or CI, unless code, tests or generated output depend on the changed docs (for example plates checked by tests, or files that scripts read). Strict only for ship, live, security, or identity. Doc copies = Normal. Label every finding blocker, nit, or unverified. The first review lists every blocker; a re-review checks only those; nits never start a round. Merge needs the reviewer PASS posted as a GitHub App review of the verdict the cloud wrote, except that hotfix; a chat PASS or a personal-account approval never counts.
- **Hotfix bypass.** <a id="hotfix-bypass"></a> Blaze's owner ruling, 2026-10-21 08:37 CT, is the authority: "hotfix: merge and deploy on green, critic reviews after." No merge before CI is green. Forge writes the fix with a regression test in a cloud agent and merges as forge0x1 when CI is green. Fix forward, no rollback. Blaze's 09:35 CT ruling, 2026-10-21: "A small hotfix of a few lines can be deployed directly by forge once tests are green; anything bigger is deployed by a cloud agent." A failed critic pass is another hotfix ([steps](runbooks/SHIP.md#hotfix)). Blaze's 09:35 CT ruling, 2026-10-21: board (Bifrost) fixes are a hotfix class. When a pull request whose title starts with hotfix: merges, the live server posts one merge handoff to the reviewer; an ack closes that line and does not need a review URL. A client timeout on live-inbox --handoff still prints the SendToAgent line.
- **Packet-first.** <a id="packet-first"></a> A new PR starts as a short packet in the issue or PR body: scope, files, plates and docs touched, tests, and out of scope. Critic PASS on that packet comes before any code. The cloud agent codes against the packet. Code review checks the diff against it. **Green sign-off** still applies.
- **Forward-motion.** <a id="forward-motion"></a> Critic issues a must-fix FIX only for wrong live behavior, for security, spend, or on-chain risk, or for a plate or OP-PROC line that would send a seat the wrong way. Anything else is APPROVE plus a linked follow-up issue assigned to the author: stale or incomplete docs that are not misleading, wording, nits, missing tests on code that is already proven, and out-of-scope work. A bug fix ships when it fixes the bug and breaks nothing; docs may follow in that issue. A feature's rule is written before merge. After round 2, only an original blocker can be a FIX; a new finding becomes an issue. A second FIX of an original blocker goes under Needs Blaze with the step it unblocks. Doc-only updates: see [Review](#review). Critic checks that the words match the code. A red check that depends on the changed docs blocks the merge, and the open-an-issue path applies only when nothing depends on them. A numeric, cosmetic, or word-count threshold that a runbook does not hard-name is within reason: a soft follow-up (APPROVE plus a linked future or a bundle), never FIX or REQUEST_CHANGES.
- **Green sign-off.** <a id="green-sign-off"></a> A cloud agent does not report or hand off until it has written the tests the change needs, run the suite, pushed, and confirmed every required GitHub check green on that head. Doc-only updates: see [Review](#review). The required CI job is `npm run test:comprehensive`. A full-suite run may ignore only the seven known-red tests in #397: `postinstall-config-e2e` (two), `infrastructure`, `agent-capabilities-routing`, `governance-service`, `install-bridges-config`, and `lookup-cache`. Any other new failure blocks. The report names the head sha, the test results, and the CI list. This does not replace **done**.
- **Cloud batch.** <a id="cloud-batch"></a> One worker cloud per PR, then that PR's critic cloud, never two live at once. Wake runs do not launch or resume a cloud. Events for a live run buffer per PR and collapse on PR plus head sha. Bifrost flushes one `batch` line on `run_end` or `ci_pass` only. A green head queues critic on `run_end` when the checks are already green, and on `ci_pass` when the run has already ended. A green event seen before `run_end` is not replayed. A red head (a required check has failed) on `run_end` goes back to the worker with the batch. A pending check waits. A buffered PR counts as in-beat, so nudge L1 does not fire while events are waiting. A flush waits when the day is over pace or weekly burn is at 75% or more, except a hotfix. A second critic FIX goes under Needs Blaze, who keeps the agent or starts a fresh one. On PR close, record the rounds and why.
- **Disk, not chat.** <a id="disk-not-chat"></a> After a compact, and on every wake, read the station, then the board, then memory, then resume the same role. Don't start a second copy. When `LIVE_URL` is unset, the board is `house/WAVEBOARD.md`. When `LIVE_URL` is set, the board is Bifrost: read the seat's cards there (`GET /cards`). Read `house/ATTENTION_STATE.md` for what needs the owner; if a house file is missing, use `templates/house/`. Card transitions are archived even when the card leaves the board.
- **You first.** <a id="you-first"></a> The human's direct message beats bot pings. Reply first. An open inbox line is not a ping: a non-empty inbox for this seat is the job. Answer the human in one line, then do the open lines before anything else. Anything a human reads should land in about three seconds. **Public voice** (account, spacing, replies) is a placeholder in `house/`. Don't open with "Locked:". If you say you will share something, do it the same turn. **Quiet** when someone only repeats CLOSED, MERGED, or LIVE.
- **Money and ship:** <a id="money-and-ship"></a> Ask first before you publish, change production, pay, touch secrets, or delete — unless `house/` names an exception. Git push only to repos named in `house/`. A "merge deploys this repo" exception is named there, one repo at a time.
